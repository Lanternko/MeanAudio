## ⚠️ 這個設計量不到小 GR —— primary 只被部分回答

預註冊問「代價如何從零長出來」。答案是：**用這個設計問不到零附近**。

limiter 只能削峰，所以要讓 integrated L\* 只降 3 dB，就已經需要 **8.40 dB 的 GR**。
本實驗能造出的最小 GR 就是 8.4 dB，而那裡代價已經是 −0.24 PQ。
**GR 在 0～8.4 dB 之間的行為仍然未量。** 要補得改成更小的 L\* 目標（1 dB 以下）
或抬高 ceiling，不是本實驗的範圍。

所以可寫的是「代價隨 GR 單調成長、在 GR ≈ 25 dB 達到飽和值的 94%、GR ≥ 43 dB 完全飽和」，
**不可寫**「代價從零連續長出」——那一段沒有資料。

## 判讀

1. **「聲音變大／變小本身扣分」與「limiter 弄壞音檔」是兩件可分開量的事，兩件都是真的。**
   065 在深處、072 在淺處都顯示：把響度鎖死之後，limited 版本仍然更差。
2. **輕度 limiting 不存在免費區間。** 能做到的最輕一檔（L\* −3 dB）就要 8.4 dB GR、
   付 −0.24 PQ。「只壓一點點應該沒差」在這個指標上不成立。
3. **代價早就飽和。** GR 25 dB 已經到飽和值的 94%，之後再壓 66 dB 只多 −0.044 PQ。
   也就是 PQ 懲罰的是「有沒有被 limiter 動過」遠多於「被壓了多少」。
4. **PC 依然是唯一偏好 limiting 的軸**（+0.098 → +0.202，單調）。與 064／065 同向。
   SongEval 量到 PC 的人類相關性最低（0.408），不宜據此說 limiting 讓音樂更好。
5. CU / CE / PC 的向下 limiting 是本實驗首次讀出（065 算了但沒報）。

## 對既有結論的影響

- 064 的「不能用 limiter 提升 LUFS 修分數」與 065 的「向下壓也不划算」**維持並補強**：
  現在 −84 dB 到 +6.8 LU 全段都有 limiter 資料，四個 AES 軸都是同一個結論。
- 要對齊兩個 arm 的響度，仍然只能用**純量**，而且方向要往下（064）。
- 絕對代價只對 x42-dpl 成立：064b 測過五種 limiter，處理代價大小差 12 倍
  （hyrax −0.009 ～ loudnorm −0.113 PQ @ T14），方向才是穩健的。

## 附帶：AES 對 batch 組成敏感（新）

6 片段的 smoke test 發現：同一份音訊（content_sha256 全同）在 batch 16 的不同組成下
AES 差到 9.3e-4，CLAP 差 0（CLAP 已逐檔）。機制是 `score_all` 把 AES 一個條件對
「當前還沒完成的 clip」一次呼叫，`todo` 變短就位移 batch 邊界。

含意：**續跑不具決定性**（與 `eval.py` 續跑同型），跨 run 比 AES 絕對值要同分組。
本次全量從頭跑，所以閘門是 0.0。詳見 memory `reference_aes_batch_composition_sensitivity`。
